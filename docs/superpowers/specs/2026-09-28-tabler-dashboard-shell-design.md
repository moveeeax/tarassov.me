# ТЗ: каркас личного дашборда на Tabler (подпроект 1 из 6)

Дата: 2026-09-28 · Статус: черновик на вычитке · Реализация отдельной веткой по плану (writing-plans)

## 1. Контекст и цель

Админка `/admin` сейчас закрывает три задачи: посты блога, медиатеку и
администрирование (пользователи, роли, джобы, аудит). Целевое состояние другое:
это личный дашборд, в который переезжают функции из рабочего пространства Notion
(14 хабов, около 45 баз по срезу 25.09.2026): заметки, журналы дня и тела,
деньги, задачи, цели, хобби, календарь.

Переезд разбит на шесть подпроектов (раздел 3). Этот спек описывает первый:
оболочку, дизайн-систему и механику настраиваемой главной страницы. Доменных
зон он не добавляет.

Отдельное требование заказчика: публичная визитка `/` и блог `/blog/*` не
меняются ни по поведению, ни по внешнему виду.

### Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Судьба Notion | Переезд зонами, без синхронизации. Зона уезжает целиком: разовый импорт истории, дальше запись только в дашборд, в Notion зона замораживается |
| Источник импорта | Notion MCP. Режим `view` как основной (квоты нет), `rows` только там, где нужен настоящий rich text |
| Модель данных | Типизированные таблицы по одной на сущность, по `docs/CONVENTIONS.md`. Универсальный движок коллекций отклонен: он противоречит разделу «What NOT to reach for» в тех же конвенциях |
| Владение данными | Таблицы с `owner_id` под `API_REQUIRE_OWNER`. Каркас на несколько пользователей, наполняет один |
| Кастомизация | Одна настраиваемая страница `/admin` с сеткой виджетов. Разделы зон остаются фиксированными страницами |
| Дизайн-система | Только Tabler. Пакет `@tabler/core` из npm, Tailwind и shadcn удаляются целиком |
| Поведение компонентов | Свои React-примитивы поверх классов Tabler. Bootstrap JS не подключается: два источника поведения на одном DOM |
| Заметки и посты | Разные сущности. Действие promote создает черновик в `posts` со ссылкой на заметку. Публичный контракт блога не меняется |
| Календарь Google | Последняя волна, вне этого спека |

Форк `moveeeax/tabler` проверен 28.09.2026 через GitHub API: он совпадает с
`tabler/tabler@dev` бит в бит (ahead 0, behind 0), лицензия MIT. Страницы
превью `tabler.io/admin-template/preview` генерируются из `preview/pages/*.astro`
этого же репозитория, а стили приходят из `core/`. Поэтому внешний вид превью
дает опубликованный пакет, и вендорить форк незачем.

## 5. Бэкенд раскладки

### 5.1 Миграция `migrations/010_dashboard_widgets.sql`

Соглашения берутся с `006_add_posts_table.sql`: `UUID PRIMARY KEY DEFAULT
gen_random_uuid()`, `TIMESTAMPTZ`, идемпотентный DDL, никаких `BEGIN`/`COMMIT`
(раннер сам оборачивает файл в одну транзакцию под advisory-локом).

```sql
CREATE TABLE IF NOT EXISTS dashboard_widgets (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id    UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    widget_type VARCHAR(64) NOT NULL,
    grid_x      SMALLINT    NOT NULL,
    grid_y      SMALLINT    NOT NULL,
    grid_w      SMALLINT    NOT NULL,
    grid_h      SMALLINT    NOT NULL,
    options     JSONB       NOT NULL DEFAULT '{}'::jsonb,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_dashboard_widgets_owner
    ON dashboard_widgets (owner_id, grid_y, grid_x);
```

Плюс триггер `dashboard_widgets_touch_updated_at` по образцу из миграции 006.

Почему тип, позиция и размер лежат колонками, а не одним json-блобом: тогда
валидация границ и сортировка остаются в SQL, а в `options` попадают только
параметры конкретного виджета. Раскладка это состояние интерфейса, поэтому
`jsonb` в поле `options` не противоречит выбору типизированных таблиц для
доменных данных.

### 5.2 Домен и репозиторий

`src/domain/DashboardWidget.hpp`: структура, `from_row`, `to_json` по образцу
`src/domain/Post.hpp`. Все поля присутствуют во всех трех местах.

`src/repositories/DashboardWidgetRepository.hpp`: `CrudBase<DashboardWidgetRepository,
Domain::DashboardWidget, std::string>` с четырьмя константами плюс
`static constexpr const char* kOwnerColumn = "owner_id";`, что включает
`find_owned` / `list_owned` / `count_owned`. `kOrderBy` это `grid_y, grid_x`.

Рукописная операция одна: `replace_all(owner, widgets)` внутри
`Database::get().execute_write([&](auto& txn){ … })`. Она удаляет набор владельца
и вставляет новый в той же транзакции. Записи, тронувшие ограничения, оборачиваются
в `detail::translate_sql(...)`. Типизированные исключения: `struct DashboardWidgetNotFound
: NotFoundError`.

### 5.3 Контракт ручек

Контроллер `src/api/DashboardController.hpp` по образцу
`src/api/ApiKeyController.hpp` (единственный owner-scoped контроллер в репозитории).

#### `GET /api/v1/dashboard/catalog`

Гард `API_REQUIRE_PRINCIPAL`. Отдает статический каталог типов, отфильтрованный
по правам вызывающего.

```json
{"data":[{"type":"posts_summary","title":"Posts","description":"Черновики, публикации, последние записи",
          "default_w":4,"default_h":3,"min_w":3,"min_h":2,
          "options":{"limit":{"type":"int","min":1,"max":10,"default":5}}}]}
```

#### `GET /api/v1/dashboard/layout`

Гард `API_REQUIRE_OWNER`. Отдает виджеты владельца в порядке `grid_y, grid_x`.
Пагинации нет, конверт `{"data":[...]}` для единообразия со списочными ручками.

#### `PUT /api/v1/dashboard/layout`

Гард `API_REQUIRE_OWNER`. Полная замена набора одной транзакцией: перетаскивание
рождает новую раскладку целиком, поэтому патчить по одному виджету незачем, а
идемпотентность выходит сама.

```json
{"widgets":[{"widget_type":"posts_summary","grid_x":0,"grid_y":0,"grid_w":4,"grid_h":3,"options":{"limit":5}}]}
```

Ответ 200 с сохраненным списком (свежие `id`).

Валидация через `Validation::Errors` и `Validation::response_400`:

1. `widget_type` есть в каталоге, иначе 400.
2. Сетка на 12 колонок: `grid_x` в диапазоне 0..11, `grid_w` в диапазоне
   `min_w`..12, сумма `grid_x + grid_w` не больше 12.
3. `grid_y` в диапазоне 0..200, `grid_h` в диапазоне `min_h`..24.
4. Не больше 40 виджетов в наборе.
5. Ключи `options` только из описанных в каталоге, с проверкой типа и границ.
   Неизвестный ключ это 400, а не молчаливое игнорирование.
6. Виджет, требующий права, которого у вызывающего нет, дает 403 (не 400: это
   вопрос доступа, а не формы запроса).

Пересечения виджетов не проверяются. `react-grid-layout` их не производит, а
проверка на бэкенде добавила бы источник 400 на ровном месте. Решение
осознанное, зафиксировано здесь, чтобы его не приняли за пропуск.

Кеш Redis для раскладки не используется: набор на пользователя маленький, а
инвалидация дала бы больше дефектов, чем экономии.

### 5.4 Каталог как единственный список

Каталог живет `constexpr`-массивом в C++ и оттуда же валидирует `PUT`. Фронт
берет его запросом и не держит свою копию. Vitest проверяет, что на каждый `type`
из ответа каталога есть зарегистрированный компонент. Так не появляется второй
список, который разойдется молча.

### 5.5 Регистрация

Роуты в `src/api/Api::get_endpoints()` внутри `src/api/Endpoints.hpp`, include
в `src/api/Api.hpp`, блок путей и схема `DashboardWidget` в `docs/openapi.yaml`

## 7. Фронт

### 7.1 Зависимости

Ставим: `@tabler/core@1.6.0`, `@tabler/icons-react@3.48.0`, `apexcharts` с
`react-apexcharts@2.1.1`, `@fontsource-variable/inter@5.3.0`,
`react-grid-layout@2.2.4`. Версии проверены в npm 28.09.2026;
`react-grid-layout` поставляет свои типы (`dist/index.d.ts`), пакет
`@types/react-grid-layout` не нужен.

Убираем: `tailwindcss`, `tailwind-merge`, `tailwindcss-animate`,
`class-variance-authority`, `@radix-ui/react-label`, `@radix-ui/react-slot`,
`lucide-react`, `autoprefixer`, `postcss`, файлы `tailwind.config.js` и
`postcss.config.js`.

`clsx` остается: он не про Tailwind. `cn()` в `src/lib/utils.ts` теряет
`twMerge` и сводится к `clsx`.

ApexCharts выбран потому, что графики в превью нарисованы им: он лежит в
`devDependencies` пакета `core`. `vanilla-calendar-pro` из его
`peerDependencies` в этом подпроекте не нужен, он понадобится в волне 6.

### 7.2 Примитивы и оболочка

`src/components/ui/*` (8 файлов) заменяется на `src/components/tabler/*` с
разметкой Tabler: `.btn`, `.card`, `.alert`, `.form-control`, `.form-label`,
`.placeholder` вместо скелетона, `.toast`. `DataTable` переходит на
`.table.card-table`, `PaginationFooter` на `.pagination`. `FormField` сохраняет
`react-hook-form` с zod, меняется только разметка.

Оболочка берется из превью: боковая `navbar-vertical`, `page-header` и
`page-body`, переключатель темы через `data-bs-theme` и localStorage.
`src/index.css` вместо токенов shadcn импортирует Tabler и держит свои
переменные темы.

Поведение остается на своих компонентах: `Modal.tsx`, `ConfirmDialog.tsx`,
`useFocusTrap`. Bootstrap JS не подключается.

### 7.3 Шрифт и CSP

В превью Inter грузится из Google Fonts, а CSP админки в `frontend/nginx.conf`
разрешает `font-src 'self'` и внешние стили не разрешает вовсе. Поэтому Inter
ставится пакетом и уходит в бандл. CSP не ослабляется, `nginx.conf` и
`helm/tarassov-me-frontend/templates/configmap.yaml` остаются без правок.

Любая внешняя ссылка внутри CSS Tabler (шрифт, картинка) молча отвалится в
прод-сборке. Проверяется в собранном виде, а не в dev-режиме Vite.

### 7.4 Сетка

`react-grid-layout` на 12 колонках, в каждой ячейке карточка Tabler. Библиотека
тянет свой небольшой CSS под подсветку места и ручки ресайза: в Tabler такого
компонента нет, и это поведение, а не тема.

Сохранение по завершении перетаскивания, с задержкой 800 мс, одним `PUT`.
Промежуточные состояния перетаскивания на сервер не уходят.

Режим настройки отдельный: пока он выключен, карточки не двигаются и не
ресайзятся. Так случайное перетаскивание при чтении не меняет раскладку.

Пустая раскладка у нового пользователя отдается пустым списком, а страница
показывает набор по умолчанию (`empty` из Tabler плюс кнопка «собрать
дашборд»), но не пишет его в базу без действия пользователя.

## 11. Замечания для исполнителя

1. Все модули под `src/` заголовочные. Новый `.cpp` там не линкуется вообще.
2. Контроллер включает `api/Guards.hpp`, `api/HandlerSupport.hpp`,
   `api/RequestUtils.hpp`, `api/Validation.hpp`, `utils/ErrorResponse.hpp`, но
   не `api/Api.hpp`: это цикл включений.
3. `callback(...)` вызывается ровно один раз на каждом пути, включая ранние
   возвраты и раскрытия гардов.
4. JSON только `nlohmann::json`. `req->getJsonObject()` не вызывается.
5. Лямбда в `execute_write` принимает `auto& txn`: внутрь приходит
   `detail::TracingTxn&`, а не `pqxx::work&`.
6. Плоский `find`/`list` на таблице с владельцем это IDOR. Только `*_owned`.
7. Осиротевшие классы Tailwind после удаления пакета не ломают верстку, а
   перестают действовать, и это тихий дефект. После каждого шага переписи идет
   `grep` по `frontend/src` на характерные префиксы.
8. Смена дизайн-системы означает, что промежуточные коммиты выглядят сломанно.
   Работа в отдельной ветке, в `main` приходит одним PR.
9. Откат в проде обычный: предыдущий тег образа фронта и ручной `helm upgrade`.
   Тег в git собирает образы, но в кластер сам ничего не выкатывает.
